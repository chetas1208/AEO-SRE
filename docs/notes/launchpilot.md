## What was studied
- `apps/api/app/models/{base,approval,execution}.py`: SQLAlchemy 2 typed models, `UUIDPrimaryKeyMixin` (`Uuid` PK, `uuid4` default), `TimestampMixin`, JSON columns via `sqlalchemy.types.JSON`.
- `apps/api/app/models/approval.py`: single `approvals` table (`status` string pending/approved/rejected, `requested_by` / `requested_by_agent`, `approved_by`, `approved_at`, `rejected_at`, `required_scope`, `requires_step_up`).
- `apps/api/app/routers/approvals.py`: REST routes `GET /projects/{id}/approvals`, `POST /approvals/{id}/approve|reject`; scope check (`approval:write`) then mutate status in place and commit. Notable weaknesses: decided approvals can be re-decided (no immutability), approve and reject overwrite each other, no model/human actor distinction, no modify path, no expiry.
- `apps/api/migrations/versions/0001_initial_schema.py`: "migration" just calls `Base.metadata.create_all` (no real autogenerated Alembic ops).
- `infra/docker/docker-compose.yml`: postgres + one-shot `migrate` service (`alembic upgrade head`) + api depending on `service_completed_successfully`.
- Workflow persistence: approvals + activity events + an external state sync after each action; no ledger/experiment concept.

## Ideas adapted (reimplemented from scratch, no code reuse)
- Approval as its own durable row with requester/decider identity, and approvals gating execution.
- Migrate-then-serve compose ordering (A14 owns compose).

## Where Profound Lift deliberately differs
- Approvals are immutable once decided (service guard + ORM `before_update` guard).
- `actor_type` (human|model|system) recorded; only humans can approve/reject/modify.
- `modified_change` stored verbatim; original change snapshot stored at request time.
- Execution requires APPROVED/MODIFIED human approval (`require_executable_approval`).
- Experiment ledger with validated status machine; reward only from measured post-intervention observations.
