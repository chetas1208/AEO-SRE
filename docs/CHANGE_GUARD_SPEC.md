# Change Guard — Experiment Protection + Cross-Agent Change Checks (binding spec)

Decision: build this as a **feature inside AEO SRE** (not a rename, not a pivot). Graduation to a standalone "merge queue" product only if real multi-agent ChangeSets arrive; until then it is a capability that strengthens the Experiment object.

Flow: Profound Agent → (Call API node) → `POST /api/change-checks` with a structured ChangeSet → AEO SRE Change Guard → one decision → the Agent continues accordingly. No "pending change" API from Profound is assumed: **Agents post their intended ChangeSets to us** (documented, real integration path: Profound Agents can run structured workflows, expose run status/step outputs via API, and call external APIs through a Call API node — verify wording against Profound docs before quoting).

Honesty: the claims about Profound's Human Review limits, Command Center scope and "20,000 agents" are user-provided and unverified — do not put them in README/UI. Do not claim Profound has no governance; the gap is cross-run semantic coordination (this change vs other active changes vs canonical truth vs active experiments). Demo data from simulated agents must be labelled SIMULATED AGENT everywhere (API field `source_mode` = LIVE | SIMULATED), never presented as real Profound Agent traffic.

## Decisions
`ALLOW | MERGE | DELAY | REQUIRE_REVIEW | BLOCK`. Precedence when several checks fire: BLOCK > DELAY > REQUIRE_REVIEW > MERGE > ALLOW. Every response lists all findings (not just the winning one), each with type, severity, references (experiment code, other change id, canonical claim id), human-readable reason, and for DELAY an `eligible_after` timestamp.

## Three checks only (do not add more)
1. **Active-experiment contamination** → DELAY. A change touching a target (normalized URL; exact or path-prefix section match) or prompt clusters overlapping an experiment that is `executing/executed/awaiting_verification` (measurement not complete) is delayed until the experiment's verification is complete (use the single window service `app/experiments/window.py` for `eligible_after`; the eligible time is the window START while the window has not opened (the earliest a measurement can begin, e.g. EXP-0001: 2026-10-04T20:29:43Z) and the window END while it is open and unmeasured; if verification is overdue no time exists, so the guard answers REQUIRE_REVIEW with an explicit reason, never a DELAY without a time; never invent times). Reuse B4's collision logic (`app/experiments/*` target_key / prompt-cluster overlap); do not duplicate it. Report target overlap % and prompt-cluster overlap %. OBSERVE-type experiments protect their target too but are reported as such.
2. **Duplicate / conflicting target changes** → MERGE (same target, same action type, claims compatible or subset/duplicate: propose merged ChangeSet) or REQUIRE_REVIEW (same target, claims that conflict, or different intents). Compared against other pending/approved-not-yet-executed ChangeSets (and AEO SRE's own pending interventions) on the same target.
3. **Canonical-truth conflict** → BLOCK. Claims in the proposal that contradict an org's canonical claims (admin-managed per organization; fields: key, statement, entities, scope, valid_from, source/provenance, status). Deterministic rules first (entity+predicate+negation/exclusivity/numeric/date mismatch), then EvidenceRanker contradiction score and, if the ModelGateway is READY, a structured-output NLI-style classification over supplied claim pairs (unknown ids rejected, output validated; the model can only classify supplied claims, never invent canonical claims). Outcome classes per pair: DUPLICATE | COMPATIBLE | DEPENDENT | CONFLICTING | UNRELATED. If the gateway/ranker are unavailable, rules alone decide and the response says `semantic_check: degraded` (never claim a semantic pass that did not run). When canonical truth is empty for the org → check skipped and reported as `skipped_no_canonical_truth` (never a silent pass).

## ChangeSet (input)
`org_id` or `org_domain`; `agent` {id, name}; `profound_run_id` (optional); `source_mode` LIVE|SIMULATED; `target_url`; `action_type` (existing ActionType vocabulary); `proposed_claims[]` (strings); `proposed_text` / `proposed_diff` (optional); `reason`; `expected_kpi`; `risk`; `reversible`; `idempotency_key` (optional; default = agent id + run id + digest).

## Action digest + approval binding
`digest = sha256(canonical_json({org, agent_id, target (normalized), action_type, claims (normalized, sorted), diff/text hash, experiment_context (ids+states of active experiments touching the target at check time)}))`. Approval binds to the digest: any change to the proposal ⇒ new digest ⇒ old approval invalid. Execution/activation (including manual execution recording and `observe` activation) **revalidates** the digest against the current stored change before proceeding; mismatch ⇒ `409 APPROVAL_DIGEST_MISMATCH`. Applies to both external ChangeSets and AEO SRE's own interventions (digest stored on the Approval row). A DELAY/BLOCK decision never auto-expires into approval; re-check on retry yields a fresh decision and digest.

## API (typed errors, OpenAPI, snake_case)
- `POST /api/change-checks` — create + evaluate (idempotent on idempotency_key: same digest ⇒ same stored decision with `replayed: true`; same key but different digest ⇒ 409). Auth: `Authorization: Bearer <CHANGE_GUARD_TOKEN>`; if the env var is unset the endpoint returns `503 CHANGE_GUARD_NOT_CONFIGURED` (secure by default; the UI/internal calls use a separate internal path/service call, never the token). Never log the token; constant-time compare; rate-limit sanely; body limit.
- `GET /api/change-checks` (filters: org_id, decision, target, experiment_code; paginated), `GET /api/change-checks/{id}`.
- `GET /api/experiments/{id}` gains `protection` {protected: bool, until (eligible_after), targets, checks_blocked_count, recent_checks[]}.
- Canonical truth: `GET/POST/PATCH /api/organizations/{id}/canonical-claims` (human actor via X-Actor; audit events; soft-retire rather than delete).
- Incident/intervention detail gains `change_guard` verdict for the proposed intervention (AEO SRE's own proposals run the same guard).
- SSE/audit events: `change_check.created`, `change_check.decided`, `canonical_claim.changed` (small payloads).

## UI (existing design language, no restyle; no new top-level tab)
Experiments page: a "Protected until <time>" badge/banner on protected experiments and a "Change checks" panel (decision chips ALLOW/MERGE/DELAY/REQUIRE_REVIEW/BLOCK, agent, target, reasons, eligible_after, SIMULATED badge when applicable). Incident/intervention Action tab: the guard verdict for the proposed intervention before approval (BLOCK/DELAY prevent Approve with explanation; REQUIRE_REVIEW shows a warning and needs a typed reason; MERGE shows the merged proposal suggestion). Settings → Organization: "Canonical truth" editor (list/add/edit/retire claims). Unknown/null = unavailable. No client-side decision logic.

## Validation / evaluation
`make eval-guard`: deterministic scenario set (experiment overlap by exact target, prefix section, prompt-cluster overlap, no overlap; duplicate vs conflicting same-target changes; canonical contradiction by negation/exclusivity/numeric/date; compatible claims; empty canonical truth; degraded semantic check; digest mismatch after edit; idempotent replay; precedence BLOCK>DELAY>…). Gates: zero false ALLOW on seeded contamination/contradiction cases, DELAY always carries a real eligible_after from the window service, no silent pass when a check could not run. Dev demo: a script `scripts/simulate_agent_change.py` (clearly SIMULATED) that posts ChangeSets such as the fixture example; against the fixture org/experiment EXP-0001 the target must yield DELAY until 2026-10-04T20:29:43Z — read-only with respect to the experiment (never verify/reward/alter it).
